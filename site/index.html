Postmortems · real incidents

  
When production broke, and what I changed

  
Running a system is mostly what happens after launch. Three incidents from 2026, written up the way an SRE team would.

  

    
SEV-1 · SITE DOWN
Database stopped answering: data transfer quota exhausted

      
Detect
Health check returned 503 "database unreachable".
Cause
Product cards loaded every photo row per vehicle: gigabytes of egress in hours.
Fix
Query reads only the main photo, duplicate scan moved into SQL, database plan right-sized.
Prevent
Query statistics enabled; egress tracked.

      
✓ restored the same day

    
SEV-2 · DEPLOYS BLOCKED
Releases failing: "no space left on device"

      
Detect
Three CI deploys failed; the SSM agent returned no output.
Cause
Old images kept 7 days filled the 30 GB disk; build cache shipped inside the image.
Fix
Live EBS resize to 40 GB, 21.7 GB reclaimed, filesystem grown online.
Prevent
Prune before pull, keep only the running image, slimmer image.

      
✓ <1 minute of downtime

    
SEV-3 · USER IMPACT
Staff could not set a main photo on phones

      
Detect
Staff report: "nothing changes"; admins unaffected.
Cause
Portal not responsive: hover-only 10 px buttons on a 390 px screen.
Fix
Responsive portals, slide-out menu, always-visible touch targets.
Prevent
Phone-sized end-to-end checks before release.

      
✓ fixed and verified same day

How this site is built and deployed
The portfolio itself follows the same practices I use in production.

  

    
    
      
  1. Infrastructure as code: one CloudFormation template creates a private S3 bucket, a CloudFront distribution with Origin Access Control, an ACM TLS certificate and security headers.
    2. 
      
  2. Keyless CI/CD: every push to main runs GitHub Actions, which assumes an AWS role through OIDC. No access keys exist.
    3. 
      
  3. Atomic deploy: files sync to S3 with long-lived caching for assets, then the CDN cache is invalidated.
    4. 
      
  4. Fast and secure: static HTML, no tracking, HTTPS only, HSTS and a strict content security policy.
    5.
